§ 00

Abstract

Protocol overview and core value proposition

AutoPerp is a decentralized, privacy-preserving perpetual futures exchange deployed natively on the Aleo blockchain. By utilizing zero-knowledge cryptography (zk-SNARKs) and Leo 4.0's cross-program invocation capabilities, AutoPerp allows traders to execute highly leveraged (up to 50×) derivatives trades while cryptographically concealing their trade sizes, liquidation margins, and PnL from the public ledger. Furthermore, AutoPerp introduces the AgentAuth Protocol, a trustless framework that enables AI agents to autonomously manage trading strategies via mathematically scoped, time-bound permission tickets — completely eliminating the need for centralized API key sharing or custodial wallets.

§ 01

Introduction

The problems AutoPerp is built to solve

1.1The State of Decentralized Derivatives

Decentralized Finance (DeFi) has democratized access to complex financial instruments, with perpetual futures emerging as the dominant trading vehicle by volume. However, the current generation of decentralized exchanges (DEXs) operating on EVM-compatible and transparent blockchains suffer from fundamental architectural flaws that actively harm retail participants.

1.2The Privacy Dilemma: MEV and Information Asymmetry

On Ethereum, Solana, and Arbitrum, every user transaction, position size, and liquidation threshold is broadcasted in plaintext to the entire network. This total transparency produces extreme information asymmetry:

⚡

MEV Front-Running

Institutional actors and MEV bots monitor mempools to front-run retail order flow, extracting value before transactions settle.

👁

Copy-Trading Exposure

Profitable traders are routinely copy-traded the moment wallet addresses are identified, permanently destroying the alpha of proprietary strategies.

⚠️

Liquidation Hunting

Visible liquidation thresholds allow adversarial actors to precisely target and trigger cascading liquidations against transparent positions.

1.3The AI Automation Dilemma: Private Key Custody

The emergence of Large Language Models has birthed massive demand for AI-automated trading. The industry's current solution, however, is structurally broken: users are forced to hand over their private wallet keys to custodial Telegram bots or centralized Python servers.

Handing a private key to a black-box server is equivalent to giving a stranger unlimited access to your bank account. AutoPerp replaces this paradigm entirely with mathematically scoped, time-bound permission tickets — the AI agent never receives private key access.

§ 02

Cryptographic Foundation

snarkVM · Leo 4.0 · Aleo Network

2.1The Aleo Network Advantage

AutoPerp is built on Aleo, a Layer-1 blockchain explicitly designed for zero-knowledge applications. Aleo utilizes snarkVM, allowing programs to be executed off-chain while only submitting cryptographic proofs of execution to the blockchain. This moves the computational burden of complex trading arithmetic off the consensus layer, ensuring absolute privacy and horizontal scalability.

autoperp_core_private_v9.aleo — record model
// Private encrypted position record — invisible to all observers record PositionRecord { owner: address, // encrypted under user view key position_size: u64, // concealed from network observers leverage: u64, // max 50x, enforced in circuit entry_price: u64, // scaled × 10000u64 liq_threshold: u64, // private — cannot be hunted is_long: bool, expiry_block: u32, }

2.2Record Model vs. Account Model

Unlike the EVM's global state account model, Aleo utilizes a Record model (analogous to Bitcoin's UTXOs but capable of holding complex data payloads). AutoPerp leverages Records to represent individual user states (TraderVault, PositionRecord). Because these records are encrypted under the user's view key, they are indistinguishable from random noise to network observers.

🔒

Off-Chain Execution

Complex proof generation happens locally; only succinct zk-SNARK proofs are published to chain — no computational bottleneck on consensus.

🔀

UTXO-Style Records

State is owned by individuals as encrypted records rather than shared global state, eliminating information leakage by design.

3.1Core Settlement Engine

The public-facing engine manages collateral deposits, liquidity provision, and trade settlement. It operates primarily on transparent mappings to ensure the overall Total Value Locked (TVL) is highly verifiable and easily auditable by the community.

3.2Private Encrypted Engine

The private core mirrors the settlement engine but operates entirely inside the zero-knowledge circuit environment. Transaction inputs and outputs are consumed and produced as encrypted Records — wallet balances, open positions, and liquidation thresholds are never publicly visible.

3.3Cross-Program Oracle Integration

A decentralized Time-Weighted Average Price (TWAP) oracle program. Through Leo 4.0's external mapping invocations, the Core and Private programs execute Mapping::get_or_use() queries into the Oracle program on-chain. This lateral data pipeline guarantees that trades only settle against hardened, verifiable consensus prices — user-supplied parameters are entirely discarded.

autoperp_core_v9.aleo — oracle cross-invocation
// Finalize block: fetch hardened price from oracle program finalize open_position( execution_price: u64, market_id: u64, ) { // Lateral cross-program oracle query let oracle_price = Mapping::get_or_use( autoperp_oracle_v2.twap_prices, market_id, 0u64 ); // Enforce ≤1% divergence for public operations let divergence = (execution_price.abs_diff(oracle_price) * 10000u64) / oracle_price; assert(divergence <= 100u64); }
§ 04

The AgentAuth Protocol

Permissioned intent execution · Trustless AI delegation

Rather than authorizing an AI to control a wallet, the user delegates narrow, provable intent. The AI agent operates from an unprivileged, standard Aleo address — cryptographic proof of permission replaces private key trust.

4.1Lifecycle of an AgentAuth Ticket

Intention Parsing Frontend · Gemini LLM

The user interacts with the AutoPerp frontend, outlining their technical strategy: "Open a 10× long on BTC if the price drops below $65,000." The LLM proxy parses the strategy into protocol parameters.

Ticket Minting autoperp_agent_v3.aleo

The frontend crafts a transaction invoking grant_auth(). The user signs this transaction, burning a small gas fee to mint an encrypted AgentAuthTicket Record on-chain, assigned directly to the AI's address.

Autonomous Execution AI Agent

When market conditions are met, the AI submits an open_position command using its own gas, supplying the AgentAuthTicket as cryptographic proof of permission. The user's private key is never involved.

Ticket Burn & Replay Protection snarkVM Circuit

Upon successful execution, the ticket Record is consumed (burned). It can never be reused. Block-height expiry provides a secondary time-bound invalidation layer.

4.2Scoped Bitmask Architecture

The core security mechanism is the permissions_bitmask applied to each ticket. Each protocol action is assigned a binary flag — mathematical enforcement replaces policy trust.

Bit Flag Permission Example Grant = 3 (0011) Example Grant = 6 (0110)
0001 Open Position ✓ Allowed ✗ Denied
0010 Close Position ✓ Allowed ✓ Allowed
0100 Withdraw Collateral ✗ Denied ✓ Allowed

By granting an authorization of 3 (0011), the user allows the Agent to open and close trades, but mathematically denies the ability to withdraw funds. If the agent attempts a withdrawal, the snarkVM circuitry rejects the proof instantly — no policy check, no admin override needed.

4.3Block-Height Expiry & Replay Protection

Every ticket contains an expiry_block constraint. If the network topology exceeds this height, the ticket is instantly invalidated by the circuit. Furthermore, tickets are consumed (burned) upon use, offering absolute protection against transaction replay attacks.

§ 05

Hybrid State Model

Solving ZK concurrency · Public accounting, private operations

5.1The Lock Contention Problem

Zero-knowledge applications face significant hurdles regarding state concurrency. If 1,000 users attempt to trade simultaneously and the protocol relies on a single PoolState Record to track available liquidity, 999 transactions will fail due to record consumption collision — the fundamental UTXO concurrency problem.

5.2Public Accounting, Private Operations

AutoPerp resolves this via a Hybrid State Architecture that cleanly separates aggregate liquidity state from individual privacy:

Public Mappings

Concurrent-friendly global aggregate state

pool_balance
pool_shares
total_open_interest
protocol_fee_accumulated
Private Records

Encrypted, individually owned state

TraderVault (wallet balance)
PositionRecord (open trade)
liq_threshold (private)
AgentAuthTicket

This decouples global liquidity from localized privacy, enabling AutoPerp to theoretically handle throughput parallel to Aleo's maximum consensus limits while maintaining complete individual position privacy.

5.3Shielded Exit Liquidity

Even when withdrawing final payouts, information leakage is prevented. The transfer_public_to_private mechanism burns requisite public pooled tokens and mints a completely unlinked, 100% encrypted Private Token Record. The block explorer registers a reduction in pool liquidity — but the destination, user identity, and exact payout size are mathematically invisible.

§ 07

Core Mathematics & Economic Security

Fixed-point precision · Funding rates · NAV-based LP issuance

Due to the absence of floating-point variables in zero-knowledge execution environments, AutoPerp enforces absolute precision through custom scaling factors — 10000u64 represents 1.0 in all protocol arithmetic.

7.1Oracle Safety Divergence Guard

To defend against malicious client-side proof generation, AutoPerp's finalize blocks calculate the divergence margin and enforce strict circuit-level constraints:

Oracle Divergence Check
divergence = |execution_price − oracle_price| × 10000 oracle_price

Constraint: divergence ≤ 100 for public ops (1%)  ·  divergence ≤ 500 for private ops (5%)

7.2Dynamic Funding Rates

Funding rates natively balance Long and Short skew by applying real-time PnL pressure. During position closure, the funding value is computed from the oracle's rate and direction bit:

Funding Value Calculation
funding_value = position_size × funding_rate 100000

Depending on funding_direction fetched from the oracle, this value is added to or subtracted from vault collateral — ensuring total economic realism.

7.3NAV-Based LP Share Issuance

Static 1:1 LP token minting creates vulnerabilities where malicious actors deposit immediately before massive pool liquidations, illegitimately claiming profits. AutoPerp implements Net Asset Value (NAV) minting to close this vector.

Minted LP Shares (Anti-Dilution NAV Formula)
M = D × S B

where D = deposit amount,   S = current total pool shares,   B = current pool balance.
Share purchasing power dynamically adjusts to the exact state of pool liquidity depth.

autoperp_core_v9.aleo — NAV share minting
// Anti-dilution NAV-based LP share issuance let pool_balance: u64 = Mapping::get_or_use(pool_state, 0u8, 0u64); let total_shares: u64 = Mapping::get_or_use(pool_state, 1u8, 0u64); // M = (D × S) / B — pool inception guard let minted_shares: u64 = if total_shares == 0u64 { deposit_amount } else { (deposit_amount * total_shares) / pool_balance };
